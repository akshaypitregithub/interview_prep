Reviewer analysis (distinct from finite test coverage and not yet evidence of the learner's own reasoning):

- **State and invariant:** After sorting `intervals_vec` by `(start, end)` ascending, `merged_intervals` stores the canonical sorted union of all intervals processed so far, with consecutive entries strictly separated (`prev.end < next.start`). Whenever `merged_intervals` is nonempty, `current_interval == merged_intervals.len() - 1` holds before and after every iteration (`0` after the first push, incremented by `1` exclusively alongside each subsequent push).
- **Branches and overlap policy:** For the first interval, `merged_intervals` is empty and pushes it as-is. For each subsequent interval `(s, e)`, sorted order guarantees `last.start <= s`. If `last.end >= s`, the closed intervals overlap or share an endpoint, so keeping `last.start` and setting `last.end = max(last.end, e)` yields their exact union without shrinking nested intervals. If `last.end < s`, `(s, e)` is strictly after `last`, and because all later intervals have `start >= s > last.end`, `last` (and all earlier output intervals) can never be overlapped again; pushing `(s, e)` and incrementing `current_interval` preserves the invariant.
- **Progress and termination:** The `for` loop consumes one element of the finite `n`-element `intervals_vec` per iteration and terminates after `n` steps.
- **Arithmetic safety and borrowing:** All `i32` comparisons avoid subtraction, preventing overflow at `i32::MIN`/`i32::MAX`. Indexing `merged_intervals[current_interval]` occurs only when `!merged_intervals.is_empty()` with `current_interval == merged_intervals.len() - 1`, preventing out-of-bounds panics and `usize` overflow. The borrowed slice `&[(i32, i32)]` is never mutated.
- **Complexity:** `O(n log(n + 1))` time (`to_vec` `O(n)`, `sort_by` `O(n log(n + 1))`, single linear merge pass `O(n)`) and `O(n)` auxiliary space (`intervals_vec` plus sort scratch buffer; output `Vec` up to `n` intervals).
